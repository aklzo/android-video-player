# 技術判断の記録(decisions)

実装中に迷った点と、その判断・理由を記録する。新しいものを上に追記する。

---

## 2026-11-03: 一覧の高速化は「前回の一覧を即表示+裏で更新」を主軸にする

**判断**: 一覧画面の読み込み改善として、(1) 最後に取得した一覧を
`cacheDir/video_list.json` に保存し、次回は即表示して裏で最新を取得する
(stale-while-revalidate)、(2) 全フォルダ/全メディアの一括取得を並列化し
`orderBy` を外して `fields` を絞る、(3) JSON パース等をメインスレッド外へ、
(4) サムネイル取得をカードのスコープに移して画面外のダウンロードをキャンセルする、を行う。

**理由**: Drive には「フォルダ配下すべて」をサーバー側で絞る API がないため、
一覧の取得はドライブ全体のフォルダ+動画/webp(実データで数千件・数ページ)を毎回
直列に取得しており、その間は全面スピナーだった。API 側の削減(2)だけでは
ページ数自体は減らないため、体感を大きく変えるのは(1)。一覧は数百 KB の JSON で済み、
対象フォルダが変わったときは使わないので誤表示の心配も小さい。

**トレードオフ**: 起動直後は最大で前回取得時点の一覧が表示される(数秒で差し替わる)。
キャッシュに含まれる thumbnailLink は失効している可能性がある(.webp がない動画のみ影響、
最新一覧への差し替え後に再取得される)。thumbnailLink を `fields` から外すと
レスポンス生成が速くなる可能性はあるが、.webp がない動画のフォールバックを失うため今回は残す。
サムネイルのメモリ上の重複排除(ViewModel のジョブ共有)は廃止し、一時ファイル → rename で
同時取得しても壊れないようにした。

## 2026-07-12: プレイリスト v1 は連続再生なし・メタデータ非正規化

**判断**: プレイリストは「作成・表示・タップで単発再生」を v1 とし、
連続再生(自動で次へ)は入れない。プレイリスト項目は動画のメタデータ
(ファイル名・サイズ・フォルダパス)を Room に非正規化して保存する。

**理由**: 要件は「作成できる・タブで表示できる」。連続再生は再生キューと
各動画のネットワーク判定・保存制御が絡むため別イテレーションとする。
非正規化により Drive への問い合わせなし(オフラインでも)でプレイリストを表示できる。
プレイリストへの追加はカード長押し(YouTube 等の慣習に合わせる)。

## 2026-07-12: 複数フォルダは「全取得 1 回+フォルダごとにフィルタ」でマージ

**判断**: 対象フォルダが複数でも Drive への全フォルダ/全メディア取得は 1 回だけ行い、
フォルダごとに配下フィルタ→マージ(fileId で重複除去、先勝ち)する。
フォルダパスは「対象フォルダ名/相対パス」形式に統一する。
設定は DataStore に JSON リストで保存し、旧単一フォルダ設定からは自動移行する。

**理由**: 全取得方式の利点(リクエスト数がフォルダ数に依存しない)をそのまま活かせる。
入れ子の対象フォルダを選んでも重複表示されない。

## 2026-07-12: 一覧タイトルは日付に加えて拡張子も除く

**判断**: フィードバックは「日付部分を除いて表示」だが、拡張子 `.mp4` も併せて除く。

**理由**: 概要欄に完全なファイル名を表示するため情報は失われず、
一覧は YouTube 的な見た目(タイトルのみ)のほうが要望の意図に合う。

## 2026-07-12: フォルダパスは一覧取得時に算出して持ち回る

**判断**: 再生画面の概要欄に表示するフォルダパス(選択フォルダからの相対)は、
一覧取得時に全フォルダ情報から算出して VideoItem に持たせ、ルート引数と
Room(保存済み用)にも保存する。再生時に Drive API へ問い合わせない。

**理由**: 一覧取得時点で全フォルダの親子関係をすでに持っている(追加コストゼロ)。
再生時の問い合わせはレイテンシとオフライン再生の妨げになる。

## 2026-07-11: ストリーミング再生+CacheWriter によるバックグラウンド保存

**判断**: 「ダウンロード完了後に再生」から「即ストリーミング再生+再生中に裏で全体保存」に変更。
実装は Media3 の SimpleCache + CacheDataSource + CacheWriter を使い、手書きの
ダウンロード処理(.part→rename)を置き換える。

**理由**: フィードバックにより、タップから再生開始までの待ち時間を無くすことが優先と判明。
CacheDataSource は再生で受信したデータをキャッシュに書き、CacheWriter は未取得範囲のみを
追加取得するため、二重ダウンロードにならず通信量への配慮とも両立する。
容量上限の設定変更が部分キャッシュへ反映されるのはアプリ再起動後になる制約があるが
(LeastRecentlyUsedCacheEvictor が構築時固定のため)、完全保存済みファイルには
従来どおり CacheEvictionPolicy が即時適用されるため実害は小さい。

**トレードオフ**: ストリーミング開始後にトークンが失効した場合(1 時間超の連続再生)、
再生エラーになることがある。open ごとにトークンを再取得することで大部分は回避できる。

## 2026-07-11: 再帰列挙は「全フォルダ+全メディア一括取得→クライアント側でツリー判定」

**判断**: 選択フォルダ配下の再帰列挙は、(1) ドライブ全体のフォルダ一覧
(mimeType = folder)、(2) ドライブ全体の動画/サムネイル一覧
(mimeType = video/mp4 or image/webp)を一括取得し、クライアント側で
parents を辿って選択フォルダ配下かどうかを判定する(DriveFolderTree)。
"root" エイリアスは files/root で実 ID に解決してから比較する。

**理由**: 当初は階層ごとの BFS(親フォルダを OR でまとめた files.list)で実装したが、
実データはひとつの親フォルダ直下に動画フォルダが 1,216 個ある構造で、
1 階層に 160 リクエスト以上必要になり破綻した(フォルダ数上限 1000 に達して
0 件になる不具合も発生)。一括方式ならフォルダ数・階層に関係なく
ページング込みで数リクエストに収まる。Drive には「フォルダ配下すべて」を
サーバー側で絞る API がないため、ツリー判定はクライアントで行うしかない。

**トレードオフ**: 選択フォルダの外にある動画のメタデータも一度取得する
(drive.readonly の範囲内であり通信量は数百 KB 程度)。
mimeType が video/mp4 以外の .mp4(誤登録)は列挙されない。

## 2026-07-11: 再生画面から戻ったら再生を停止する

**判断**: 再生画面を「戻る」で離れたら再生を停止する。バックグラウンド再生が継続するのは
ホーム画面へ移動・画面オフ・他アプリへの切替のとき。

**理由**: 一覧に戻った後も音声だけ流れ続けると、アプリ内に停止手段が通知しかなく混乱する。
仕様の「アプリを離れても・画面をオフにしても継続」はホーム/画面オフを指すと解釈した。

## 2026-07-11: サムネイルの保存先は cacheDir、動画は filesDir

**判断**: 動画キャッシュは `filesDir/video_cache/`(仕様どおり)、サムネイルは
`cacheDir/thumbs/` に置き、Room では動画のみ管理する。

**理由**: サムネイルは数十 KB と小さく再取得も安価なため、OS がストレージ逼迫時に
自動削除してよい cacheDir が適切。LRU 管理(Room)の対象は動画のみでシンプルに保てる。

## 2026-07-11: フォルダブラウズはマイドライブ起点のみ

**判断**: フォルダ選択はマイドライブ(root)起点のツリーのみ対応し、
共有ドライブ・「共有アイテム」起点のブラウズは初期版では対応しない。

**理由**: 仕様の主ユースケースは自分の Drive フォルダ。共有ドライブ対応は
files.list のパラメータ追加(driveId 等)で後から拡張できる。

## 2026-07-11: Credential Manager の扱い

**判断**: 認証の主経路は AuthorizationClient とし、Credential Manager(GetGoogleIdOption)は
`local.properties` に `google.webClientId` がある場合のみ使う。

**理由**: Credential Manager で Google アカウントの ID トークンを得るには
Web アプリケーション用クライアント ID(serverClientId)が必須だが、
Google Cloud Console には Android 用クライアント ID のみ登録済みと聞いている。
一方 AuthorizationClient.authorize() はパッケージ名+SHA-1 で解決されるため追加設定不要で、
アカウント選択 UI・同意画面・アクセストークン取得・サイレント再認証のすべてを満たす。
本アプリはバックエンドを持たず ID トークンの用途がないため、機能要件は
AuthorizationClient のみで完全に満たせる。Web クライアント ID が用意されたら
`local.properties` に設定するだけで Credential Manager 経由のサインイン UI が有効になる。

## 2026-07-11: Drive API クライアントを自作(OkHttp 直叩き)

**判断**: google-api-services-drive(公式 Java クライアント)を使わず、
OkHttp + kotlinx-serialization で `files.list` / `files.get?alt=media` を直接呼ぶ。

**理由**: 公式クライアントは Apache HTTP 等の重い推移的依存を持ち Android と相性が悪い。
必要なエンドポイントは 2〜3 個だけで、インターフェース(`DriveApiClient`)を切って
モック可能にする方針とも合う。

## 2026-07-11: DI は Hilt を使わず手書きコンテナ

**判断**: Application に `AppContainer` を手書きする。

**理由**: 依存オブジェクトが 10 個未満で画面も 5 つ。Hilt の導入コスト
(kapt/ksp 設定・学習コスト)に見合わない。CLAUDE.md の「過度な抽象化はしない」に従う。

## 2026-07-11: 「Wi-Fi のみ」判定は NOT_METERED で行う

**判断**: 設定名は「モバイル回線でもダウンロード」だが、実際の判定は
`NET_CAPABILITY_NOT_METERED`(非従量制かどうか)で行う。

**理由**: ユーザーが守りたいのは通信量。Wi-Fi テザリング(従量制)を Wi-Fi 扱いで
許可してしまうより、従量制判定のほうが意図に合う。
